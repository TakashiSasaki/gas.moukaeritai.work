🤖 Development Context: Drive Shallow Mover

This document outlines the architectural decisions, coding rules, and constraints established during the development of the "Drive Shallow Mover" application. Future coding agents should adhere to these guidelines to maintain consistency and functionality.

1. Project Overview

Goal: A Google Apps Script (GAS) web application to search, filter, and move files within Google Drive without recursive directory traversal.

Core Philosophy: "Shallow" operation. Only interact with files directly under the specified folder (or root). No deep recursion.

2. Mandatory Coding Rules

CRITICAL Single-File Architecture

Do NOT separate CSS or JavaScript into different files (e.g., Stylesheet.html or Script.html) included via GAS templates <?!= include(...) ?>.

Reason: The preview environment (Gemini Canvas) cannot render server-side GAS template includes. To ensure the UI can be previewed and debugged in real-time within the Canvas, all CSS and JavaScript must be embedded directly within Index.html.

CRITICAL Mock Data for Preview

The Index.html must detect if it is running outside of the GAS environment (i.e., typeof google === 'undefined') and switch to a Mock Mode.

  • Search, Folder Picker, Fetch All, and Analysis functions must return dummy data.
  • Use setTimeout to simulate network latency.
  • This allows visual verification of UI states (loading, tables, badges) without deployment.

PERFORMANCE Concurrency & Locking

Since GAS does not handle concurrent execution for the same user state well in this context:

  • Server-side: Use LockService.getUserLock() in Code.gs. If the lock cannot be acquired within 2 seconds, throw a SERVER_BUSY error immediately. Do not wait long.
  • Client-side: Implement a `runWithRetry` mechanism. If `SERVER_BUSY` is returned, automatically retry after a short delay and show a "Waiting..." status to the user.

API Drive API v3 Usage

Use the advanced Drive service (v3).

  • Search: Construct the q parameter string dynamically based on UI inputs.
  • Move: Use Drive.Files.update with `addParents` and `removeParents` fields.
  • Query Construction: Users do not write raw queries. The UI constructs them. Clicking the query display area should reopen the settings accordion.

3. UI/UX Specifications

Layout & Responsiveness

  • Responsive: Must use <meta name="viewport" ...> and CSS media queries. Minimize padding/margins on mobile devices (< 600px).
  • Accordion: The search settings section is collapsible. It auto-closes upon search execution.
  • Tabs: Search results are split into "Folders" and "Files" tabs. Default to the tab that has content.
  • Scrolling: Result tables have `max-height` (approx 500px) with internal scrolling to prevent the "Move" section from being pushed too far down.

Visual Feedback

  • Badges: Real-time count of total items and selected items.
  • Icons: Use file-type specific emojis (📄, 📁, 📷, etc.) in the file list.
  • Progress: "Fetch All" button shows elapsed seconds. "Analyze" button updates individual rows asynchronously.

4. Evolution History & Key Decisions

  • Naming: Changed from "Manager" to "Mover" to accurately reflect its limited scope (moving files, not general management).
  • Filtering: Added "Name does not contain", "Description contains", "Full text contains", Date ranges (absolute/relative), and Size ranges.
  • Analysis: Implemented a "Analyze Breakdown" feature that fetches counts of children (folders/files) for listed folders using server-side caching (CacheService) to reduce API calls.
  • Style Consistency: Removed white background boxes from Date/Size filters to match the flat design of other fields.
