🤖 Development Context: Drive Shallow Mover

This document tracks the technical architecture, constraints, and operational rules for the Drive Shallow Mover project. Adherence to these standards is mandatory to maintain compatibility between the Gemini Preview environment and GAS production.

1. System Architecture

Architecture Hybrid Loading Strategy

The application uses a three-file structure to enable real-time UI previewing and full backend integration:

  • Index.html: Contains the UI layout, CSS, and Mock Functions. Mocks allow testing in the Canvas environment where google.script.run is unavailable.
  • JavaScript.html: Contains the production logic. It overrides mock functions in the global window scope when evaluated by the GAS template engine.
  • Code.gs: Server-side implementation. Must include a include(filename) helper to inject JavaScript.html into Index.html.

2. Backend & API Constraints

Critical Drive API v3 Update Protocol

When moving files/folders via parent updates using Drive.Files.update:

  • The 3rd argument (mediaData) MUST be null.
  • Parent changes (addParents, removeParents) MUST be passed within the 4th argument (options).
  • Failure to follow this signature results in silent failures or internal server errors.

Critical Search Query (q) Parameters

To prevent Invalid Value errors during drive.files.list calls, observe the following field restrictions:

Target Field Status Requirement / Alternative
size ❌ Forbidden Filtering by size must be performed post-fetch on the server or client.
description ❌ Forbidden Use fullText contains '...' (searches name, body, and description).
modifiedTime ✅ Supported Must be an RFC 3339 / ISO 8601 formatted string.
Single Quote (') ⚠️ Dangerous All user-provided string values must have quotes escaped as \'.

3. Query Construction Specifications

Logic updateQuery(shouldSave) Implementation

The client-side query assembly logic must adhere to these specific Drive API mappings:

  • Markdown Search: Uses OR logic to capture inconsistent MIME types:
    (mimeType = 'text/markdown' or (mimeType = 'text/plain' and name contains '.md'))
  • Exclusion Filters: Supports up to 5 keywords using not name contains '...'.
  • Relative Dates: "Days ago" values must be calculated into a fixed ISO string before assembly.
  • Location Scope: Defaults to 'root' in parents if no specific ID is provided.

4. UI Logic & Interaction Rules

UI/UX State Management (Reset-First Rule)

To avoid regressions where input fields remain grayed out or unusable:

  • The Rule: When toggling conditional input groups (e.g., Date Modes), first disable and hide ALL groups in that set. Then, enable only the one corresponding to the active mode.
  • Dual-Lock Mechanism: Apply both the disabled HTML attribute and the .input-disabled CSS class to elements.
  • Restoration Safety: Initialization/Restoration must call toggleDateInputs(false) to prevent default values from overwriting existing settings in the PropertiesService.

5. Performance & Concurrency

Performance Locking and Sequential Processing

  • Server Lock: Use LockService.getUserLock() with a 2-second timeout. Return SERVER_BUSY for retries.
  • Client Retry: Wrap API calls in runWithRetry to handle busy signals with a 1.5s delay.
  • Batch Operations: For file movement, the client-side must iterate over IDs and send one request per file. This ensures progress tracking and prevents script timeouts for large selections.

6. Data Persistence

Sync Auto-Save and Restoration

  • Debounce Save: Persistence is triggered via debounceSave(settings) after a 1-second delay from the last user input.
  • Input Coverage: All interactive inputs (including destFolderId manual edits) must trigger updateQuery(true) on the oninput event.
  • Restoration Flow: initApp in JavaScript.html fetches the settings JSON and maps keys directly to DOM Element IDs.
